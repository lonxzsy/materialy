## 2. Что сделано в этой итерации

### 2.1. Исправление online и offline playback

Корневые причины:

1. `DirectStreamResolver` перехватывал любой HTTP URI и отправлял его в Innertube, включая `127.0.0.1`, обычные прямые потоки и не-YouTube URL.
2. Online `MediaItem` строился из `fileUri`, где мог находиться истёкший `googlevideo` URL или временный loopback endpoint, вместо стабильного `sourceUrl`.
3. Library блокировала нажатие online-трека отдельной backend health-проверкой, хотя playback поддерживает прямое разрешение YouTube URL.
4. `sourceType=download` ошибочно классифицировался как remote-контент.
5. При ошибке resolver возвращал исходную HTML watch-page в ExoPlayer, скрывая реальную причину за parser error.

Исправления:

- `playback/DirectStreamResolver.kt`
  - добавлен `SourceUriPolicy`;
  - Innertube вызывается только для YouTube URL/ID;
  - CDN, loopback, local и обычные HTTP-потоки обходят Innertube;
  - ошибка resolution теперь передаётся как `IOException`, а не как попытка декодировать HTML.
- `playback/PlayerManager.kt`
  - remote playback использует стабильный `sourceUrl`;
  - local/download использует `content://`, `file://` или реальный путь;
  - пустые/невалидные источники дают понятный `PlaybackState.Error`;
  - download/local больше не получает YouTube `ContentId`;
  - `Context.mainExecutor` заменён на `ContextCompat.getMainExecutor(context)` для minSdk 26.
- `ui/screens/library/LibraryScreen.kt`
  - удалена блокировка online playback локальным health-check.

Добавлен `app/src/test/java/com/materialy/music/playback/SourceUriPolicyTest.kt`: 5 тестов для YouTube URL/ID, loopback, CDN, direct HTTP и local/download cases.

### 2.2. Видимые состояния загрузки

Файлы:

- `work/TrackDownloadManager.kt`;
- `work/DownloadWorker.kt`;
- `ui/screens/download/DownloadScreen.kt`.

Сделано:

- WorkManager-задачи помечаются общим tag и наблюдаются как `Flow`;
- реестр metadata хранится в `SharedPreferences`, поэтому список переживает навигацию и process recreation;
- состояния: `QUEUED`, `DOWNLOADING`, `FAILED`, `COMPLETED`;
- UI показывает процент, текущий этап, ошибку, retry, cancel и remove;
- `DownloadWorker` возвращает `file_uri` и `song_id`;
- completed download можно удалить вместе с файлом и Room row;
- retry создаёт новую задачу;
- локальный `registryRevision` немедленно обновляет UI после add/remove/retry;
- убрано прежнее ожидание после `SUCCEEDED`.

Ограничение: это всё ещё WorkManager/file pipeline, а не целевой Media3 `DownloadManager`/`DownloadService`.

## 4. Следующему агенту: обязательный порядок продолжения

### Шаг 1. Финальная compile/test/lint проверка

```powershell
$env:GRADLE_USER_HOME='C:\code\materialy\.gradle'
$env:ANDROID_USER_HOME='C:\code\materialy\.android'
.\gradlew.bat --stop
.\gradlew.bat --no-daemon testDebugUnitTest assembleDebug lintDebug
```

Не создавать lint baseline и не отключать ошибки. Проверить, что итог — `BUILD SUCCESSFUL`. Предупреждения разобрать по приоритету; как минимум проверить security, foreground services, exported media service и Compose performance.

### Шаг 2. Release/R8

```powershell
.\gradlew.bat --no-daemon assembleRelease
```

Ожидается долгий `minifyReleaseWithR8` с потреблением до ~3.2 GiB RAM. Это наблюдалось как активный процесс, а не зависание. Текущий `org.gradle.jvmargs=-Xmx4g`.

Если release успешен, он будет unsigned без пользовательского signing key. Не называть его production-signed. Для публикации нужны отдельные keystore/секреты и согласованный signing config.

### Шаг 3. Проверить APK

- получить SHA-256 для debug и release;
- проверить размер/время;
- выполнить `aapt dump badging`;
- установить debug APK на реальное устройство или эмулятор;
- проверить cold start, разрешения уведомлений, foreground services и отсутствие crash.

### Шаг 4. Runtime acceptance на Android

Минимальная матрица:

1. Local `content://` и app-specific downloaded `file://` playback.
2. YouTube result из Home и Search.
3. Pause/resume/seek/next/previous через UI и notification.
4. Ошибка сети показывает Retry и не уничтожает queue.
5. Download: queued → progress → completed → offline play → remove.
6. Failed download → retry.
7. Force-stop/process recreation: queue/index/position восстановлены с допуском ≤5 секунд.
8. Airplane mode: local/downloaded играют; remote быстро переходит в error.
9. TalkBack: Home → MiniPlayer → Player → Queue; reorder без drag.
10. Font scale 200%, compact/landscape/split-screen.

Без этих проверок нельзя честно ставить статус Production Ready.

## 5. Оставшиеся архитектурные и product gaps

Даже после устранения текущих багов исходный большой roadmap не завершён:

- `MediaLibrarySession.Callback` browse/root/children/search/item и настоящий `onPlaybackResumption`;
- queue sections Now Playing / manual Next / AutoMix и resolver произвольного `ContentId`;
- Media3 `DownloadManager`/`DownloadService` вместо WorkManager;
- полные album/artist/playlist detail routes и federated typed search;
- responsive rail/list-detail/supporting panes;
- локальный Roboto Flex;
- Room FTS/Paging;
- lyrics cache/rematch;
- Baseline Profile/Macrobenchmark;
- instrumentation/Compose/Media3 integration/accessibility tests;
- Android Auto/Bluetooth browse и Cast;
- release signing;
- юридическая/policy проверка YouTube streaming/offline.

Поэтому текущий корректный статус: **stabilized debug candidate / production work in progress**, не Production Ready.

## 6. Известные предупреждения и решения

- `Virtualizer` Android API deprecated — функционально собирается, но его следует удалить или заменить безопасной capability-based реализацией.
- `PlaybackService` exported warning требует осознанного решения: MediaLibrary/Android Auto обычно требуют exported service. Не ставить `exported=false` без проверки внешних controller use cases.
- В проекте остаётся много hardcoded UI strings; перенести в `strings.xml` перед локализацией.
- Старые скрытые server settings остаются за недоступными ветками (`showSettings=false`); физически удалить после очистки ViewModel API.
- R8 очень медленный на текущем окружении; не прерывать, пока Java процесс активно потребляет CPU.
